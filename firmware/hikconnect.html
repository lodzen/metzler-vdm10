Hik-Connect / EZVIZ cloud channel — registration and call-state pushes

How hicore (Metzler VTH 2.0.24, a rebranded Hikvision indoor station) talks to the Hik-Connect / EZVIZ cloud. Evidence: vdm10_1.0/ezviz/*.c (app layer, protocol/ezviz_*.cpp), vdm10_1.0/ezdevsdk/*.c (SDK subcore), and vdm10_1.0/misc/dclog.c (SDK transport internals). The SDK kernel itself is largely external (/* ext */ markers) — internals cited here are recovered from call sites, log strings and the few decompiled subcore files.

1. ezDevSDK and the layered architecture

Layer

Code

Role

App

protocol/ezviz_*.cpp, route/ezvizRoute.c, transProtocol/ezviz_trans_parse.cpp, functions/ezviz_send_stream.cpp

registers per-domain callbacks, builds JSON/records, drives local SIP on app commands

ezDevSDK subcore

statically linked, subcore/* + userpace/src/domain/* (jenkins tree Frontend.Civil.All-SDK, trans_parse2.c header)

framed+digested channel to DAS, LBS/DAS bootstrap, MQTT transport, P2P/UDT NAT traversal, per-domain streams

Cloud

push delivery, call signaling, alarm store, OTA, remote view

ezDevSDK is Hikvision’s embedded cloud SDK: the device never speaks HTTP or push-protocol directly to Hik-Connect — it opens one framed channel to a DAS (device access server) reached through an LBS bootstrap, then multiplexes “domains” (base, preview, talk, third-party, alarm) plus kernel-extend channels (“sub” :3700, “special” :3999) over it.

7. Call-state pushes — what produces the Hik-Connect cards

Three distinct mechanisms; only the first is the SIP-driven push:

(a) Third-party-domain call push (the user-facing cards). ezviz_third_party_send_call(callState) @0x003de520 sends svc 0x348e (“pu2opentransferdata”) with fields Authorization="", DevSerial, Token, MsgSeq=uuid, AppKey (cfg+0x3288c), Destination, Type, Data = {"push_setting":{"alert":"<utf8 GBK name>"}} plus a sound tag com.hikvision.4530.ring:{0|1|2}. Alert names (callAlertTable @0x006d8a40): 0 “call income” (收到一条呼叫), 1 “hangup” (收到一条挂断), 2 “answer” — only 0 and 1 are ever sent by the call path. A 0→1 sequence with no app answer renders as the “call declined / missed call” card.

Caller site

Action

send_call(1) then state → 0

Gating (all required for the ring push — audio.c + caller table):

  • netAltRoute()/srv_isMainRoom (FUN_000f86b0) — main-room device only;

  • cloud bound: ezviz_user_id_valid() and ez_dev_mode_get()==2 (FUN_000549d8; ==2 selects the direct push path, else the mq/alarm path — the mode semantics are marked unverified in names/ezviz.tsv);

  • ring-delay byte elapsed (per-session cfg byte, exact source unverified);

  • caller devType class (sess+0x7c via devTypeFromNum) not in {7,8,0xb} — sub-door index classes / indoor-only modes are suppressed; main door 1/5, door 2, generic 3/4/6/9 are pushed;

  • caller number ≠ "1000000000" (the room base = self).

(b) Alarm-domain call record (call log + JPEG). When ez_dev_mode_get()!=2 the same events are queued as 0x48-byte {type,channel,handler[0x40]} msgs on /ezviz_talk_message (g_ezvizCallMq); ezviz_talk_task @0x003ded74 replays them: type 0 → ezviz_ext_start_talk → ezviz_ext_push_alarm_call_hangup(0) @0x003dc87c builds a 0x14c record {ver 2, channel, time, alarmType 1, caller "N-N-N-N", handler, callUuid "<ts>-<devno>-1-00000-<rand>", callType 4} with a JPEG snapshot (ezviz_decapture), types 1/2 → hangup record (alarmType 3/2). Sent via the TLS alarm channel.

(c) Poll replies. Third-party apiId 1 getcallstate and HCNetSDK cmd 0x126020 report tp_get_call_state-1 (0 idle / 1 calling / 2 talking; the app-session states 4/5 collapse to byte 1 “Error-ish” — no push is generated for them). apiId 3 callsignal cmdId 2/3/4/5/6 = answer / refuse / ringover / over / busy → the appUASCall*Proc handlers above (rc 1 or 0x7a0–0x7a7).

9. What the simulator does / doesn’t need

The sim never speaks to the cloud — which is fine, because the push path lives in the main indoor’s firmware, not the callee’s:

Sim behavior

Cloud consequence

Local SIP plane only (--sip-host PBX / Linphone bridge)

none needed — the EZVIZ enable flag cfg+0x328d0 can stay empty; supervisor then skips start_ezviz_service entirely

Door call rings a real main indoor

the main indoor itself pushes state 0→1; our sim only affects whether the call looks “answered” (200 OK → BYE = normal hangup) or “declined” (4xx/timeout → missed-call card) — exactly the cards described in docs/protocol.md §7

Remote answer via Hik-Connect app

not reproducible: needs DAS + third-party domain + token; the app’s apiId 3 callsignal and HCNetSDK tunnel terminate in firmware code the sim doesn’t run

Remote view / talkback from the app

not reproducible: preview/talk domains + P2P/UDT + EzvizStreamBuf machinery

Remote unlock from the app

sim-side equivalent is the SIP INFO DTMF / locknumXML path, not the cloud apiId 2

Missed-call cards for calls TO the sim

only if the sim registered its own cloud account — out of scope; implementing it would mean the 0xE9ACBA9E frame + digest + STUN/MQTT registration + domain channels
