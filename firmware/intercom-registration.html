Intercom registration & private-SIP communication — firmware internals

How hicore (Metzler VTH 2.0.24, rebranded Hikvision indoor station) registers as an indoor-station/extension, keeps the binding alive, and resolves peers — i.e. the device side of the “private SIP” layer. The wire-level description of the same dialect is in ../protocol.md; this doc is what the firmware actually executes.

Sources: vdm10_1.0/sip/{README.md,xml_proc.c}, vdm10_1.0/sip/client/*, vdm10_1.0/sip/server/*, vdm10_1.0/visnet/visnet_server.c, vdm10_1.0/misc/{net_sipClient_sip_client.c.c,net_sipServer_registrar.c.c, dataManagement_database_db_api.c.c,util_common_visUtil.c.c,grouped.c}, plus ANALYSIS.md §3/4/5/8/9 (verified-live facts).

Body always comes from _sip_xml_get_reg_info_xml (xml_getRegInfoXml @0x000eb2e4, vdm10_1.0/sip/xml_proc.c) — the kind is passed straight through as the builder’s mode selector:

  <regDevMacAddr>xx:xx:xx:xx:xx:xx</regDevMacAddr>   <!-- always -->

</regXML>

(The <version> element from ANALYSIS.md §4 is not emitted by this build’s builder — unverified where it came from.)

Digest: eXosip_add_authentication_info(user, authuser, passwd, "MD5", NULL) before send; a 401/407 is resent automatically by eXosip_automatic_action (REGISTER_FAILURE path) or, for MESSAGEs, by eXosip_default_action after re-adding auth info (ack_tail.c ev 12/31). Wire challenge observed: WWW-Authenticate: Digest realm="Hikvision", nonce, opaque — MD5 only. The 401 can be emitted by send_reply’s status table (below), but no digest verification or WWW-Authenticate generation exists anywhere in the decompiled net/sipServer code — the challenge origin is unverified (the "Hikvision" rodata string exists at ~0x62e7a2; its SIP-side consumer was not located — possibly in the undecompiled srv_parseMsg/srv_forwardRequest path or the vendored eXosip).

3. Registrar pipeline — sip_registerMode @0x000d8dcc (vdm10_1.0/sip/server/registrar.c)

sip_receiveMsg (0x000db23c) → sip_parseMsg → sip_udpProcRule → REGISTER:

  1. parse_message (0x000d7b40): To, Call-ID, CSeq required; Expires parses (parse_expires @0x000cd9f4, digit accumulator); every Contact hf parses. Failures set g_reg_status @0x00a6c080 (0xe..0x13).

  2. extract_aor (0x000d77a4): To-URI user part, %-unescaped → call_num. extract_host (0x000d79e0) likewise demands an 11-char From user elsewhere.

  3. Record fill — 0xb0-byte dev_reg row: +0x04 call_num[0x14] (the AOR, must be exactly 11 chars else status 0x1a), +0x18 dev_ip[0x10] (source IP, not the Contact), +0x28 reg_time[0x20] (now+Expires as text), +0x48 dev_type, +0x4c serial_no[0x30], +0x7c mac_addr[0x14], +0x90 dev_name[0x20]. dev_type/serial/mac/name are scraped by strstr from the raw body, not XML-parsed — <regDevSerial>, <regDevMacAddr>, <regDevName> (caps 0x30/0x14/0x20).

  4. srv_splitDevNum (FUN_000f9418, misc/util_common_visUtil.c.c) derives dev_type from call_num (table below). On a subordinate registrar (FUN_0006498c()||FUN_00064c84() — cfg u8@0x2d335==0 class flag) the registering number must share the local site prefix (type digit cfg+0x2d330, floor cfg+0x2d332, unit cfg+0x2d334), and type-3 ROOM registrations are refused on analog systems (srv_isDigitalSys()==0 → "VIS_DEV_TYPE_ROOM can't reg").

  5. Expires == 0 → unregister: db_reginfo_del with where serial_no='<s>' or dev_ip='<src ip>', FUN_000fdd54 drops the call_num map, ACS password rows where room_num='<atoi(call_num+6)>' deleted, send_reply → 200.

  6. else dpi_register_dev_reg_info (below); on derived type 3 also FUN_000fdca4(dev_name, call_num) (room map) — then send_reply and vns_registrarSyncHook (§8).

Replies: send_reply/sl_send_reply/build_res_buf_from_sip_req (0x000d8cd0/0x000d8ab4/0x000d7fa8) — stateless, sendto back to source IP port 5060 (hard-coded htons(5060) — not the Via port). Status→code via g_reg_status-indexed table @0x00a6c084: 400 Bad Request, 401 Unauthorized, 500, 503, 410 Sip Gone, else 200 OK. The builder injects ;received=<src> + ;rport=5060 into the top Via and a CRC16-CCITT (crcitt_string_array @0x000d88a4, seed b57ecd3250693a8f077639fd0317176b- over {callid, cseq, from-uri}) ;tag= into To for codes <300.

Verified live (2025-11-19, LAN 10.0.0.0/24, registrar …:5065)

  • 11-char AOR: 12-char call_nums (e.g. 100000000010) all return 410 before dedup — the length check is first and nothing is inserted.

  • dedup table confirmed: 10000000001 → 410 (held by the real indoor @10.0.0.47, dev_type 3); …02, …04, …09 → 200 (inserted). 410 therefore means “call_num bound to a different serial and IP of the same dev_type” — it is not a generic “occupied” signal.

  • stale rows block: probe rows left behind by earlier runs (same call_num, foreign serial, foreign dev_ip — e.g. another host/container) keep the slot at 410 until deleted or TTL-expired; dedup never consults reg_time.

  • unregister: Expires: 0 → 200 OK and deletes where serial_no='<s>' or dev_ip='<src>' — verified both forms live (2025-11-19): empty body deletes via dev_ip alone (foreign-serial probe for the same call_num got 200 = row gone, not 410), regXML body adds the serial_no match which also clears stale rows of our serial from other source IPs. Prefer the bodied form.

  • no sync push on unregister: the Expires==0 path in sip_registerMode deletes + send_reply and returns without calling vns_registrarSyncHook (only the insert path calls it). The registrar’s row is gone (slot free, calls no longer routed), but the dev_reg table copies pushed over visNet :8102 keep the stale entry on every other unit’s device list until the next INSERT-triggered push or row expiry — an unregister can never clear another unit’s display immediately.

  • post-insert stall: after every successful insert the registrar runs vns_registrarSyncHook on the sipServer task — blocking TCP :8102 connects to every 1000000000-series row (stale/offline rows cost a connect timeout each) — and ignores REGISTERs for ~5–10 s meanwhile. Sweep probes must run sequentially, and post-200 unregisters need retries to get through the window.

  • free_extension verified end-to-end: one consistent probe (serial+MAC) → …01=410, …02=200 → unreg → 10000000002 reported free, matching the installation’s real first free slot.

6. Heartbeat MESSAGE and the sipCmd virtual AOR

task_sipClient_HeartBeat → sipcli_send_msg/_client_handle_send_sip_cmd (@0x000dc9b0): MESSAGE sip:sipCmd@<registrar-ip>:5065, Content-Type: text/xml, body from _sip_xml_get_sip_info_xml (@0x000ea910). Verified fields from the task: method=1, action=1, <from><deviceSN/><ipAddr> = own ip, <to><ipAddr> = registrar ip block (cfg+0x5fd0), body <num> = own 11-digit devLongNum (cfg+0x2d354):

<videoIntercomMsg><header><method>1</method><action>1</action>
<from><deviceSN>…</deviceSN><ipAddr>10.0.0.x</ipAddr></from>
<to><ipAddr>10.0.0.38</ipAddr></to></header>
<body><num>10000000001</num></body></videoIntercomMsg>

Registrar side (lookUp @0x000d9658, vdm10_1.0/sip/server/reply.c): AOR "sipCmd" is a virtual name — it strstrs the body for <method>1</method><action>1</action>, scrapes <num> (truncating at 11 chars — the closing tag is cut by num_buf[0xb]=0), searches where call_num='<num>', and returns 1 only while that registration is unexpired; srv_forwardRequest then answers 200 OK directly (no forward). So the heartbeat doubles as a registration-freshness probe. (<num>1</num> as sent by the sim truncates to a garbage call_num → this path predicts −1/404; the 200 OKs seen live may come from the fallback msg+0xd0=own-IP forward to the box’s own :5060 UAS — unverified.)

8. Post-register visNet sync — TCP :8102

vns_registrarSyncHook (FUN_000f1490, misc/net_sipClient_visNetServer.c.c, called at the end of sip_registerMode on success): enumerates the dev_reg table and, for each 1000000000-prefixed record, TCP-connects to that device’s :8102 and pushes cmd 0x2033 — a 0x420 packet carrying up to six 0xb0 dev_reg rows. The receiver (vdm10_1.0/visnet/visnet_server.c) stores them into g_extRoom and re-registers each locally. Net effect: after every successful REGISTER, the registrar mesh-syncs the extension table to all extensions — this is the :8102 connection observed right after REGISTER (not merely a liveness probe; the table push is verified, a separate liveness role is not).
