Simulator architecture

src/metzler/ — a Python indoor station for the Metzler/Hikvision video intercom. It registers as an extension on the main indoor station’s private registrar, accepts proprietary intercom/door calls, and bridges them either to a standard SIP endpoint (hosted provider or PBX) or to a local headset.

Everything runs in one process. The standard library covers all core paths; cryptography is needed only for SRTP on the provider leg.

Run modes

Mode

Selected by

Behavior

Provider bridge

--sip-host + --sip-target

registers on the provider (if credentials are set), forwards each indoor call as INVITE sip:target@provider, relays audio (and video for door calls)

PBX trunk

--sip-host <pbx> without credentials

same bridging, no provider REGISTER — the PBX authenticates our IP

Local headset

no --sip-host

answers indoor calls on the local mic/speaker (auto_answer policy: extension, all, none)

Outbound

--call <num> / --call <num>@<ip>

places a station→station call through the registrar or directly at ip:5060

Inbound bridge

--inbound-target <num>

a call from the SIP app rings <num> on the intercom and bridges the legs (declines 486 without it); --sip-from sets the caller-ID the app sees ({num} = the calling station’s number)

SipProvider is only constructed when --sip-host is set and local mode is off. Registration on the provider is skipped when --sip-user/--sip-pass are empty (needs_register()), which is the PBX-trunk case.

Call dispatch (inbound)

core.handle_datagram → request router → bridge.on_invite:

  1. _provider_loop_guard — ignore our own provider fork (Call-ID remembered even after the call ends), decline INVITEs arriving from the provider address (486) so a call can never be bridged back into the same account.

  2. 100 Trying + 180 Ringing (with our to-tag) to the indoor caller.

  3. Classify: real m=audio in the offer → kind="door" (two RtpRelays); header-only SDP → kind="intercom" (SipIntercomMedia).

  4. provider.invite(call) — the provider leg carries fresh Call-ID/CSeq.

  5. On provider 200 OK: answer the indoor caller in its dialect (sdp_answer_talkback for intercom, sdp_answer_firmware for door), bind SRTP keys per stream, connect media.

Local mode swaps step 3–5 for answer_locally (IntercomMedia or LocalMediaBridge against ALSA/ffplay per the auto_answer policy).

Media model

  • Intercom/extension calls (firmware type 3): no m= lines at all. Media = symmetric RTSP pulls — the caller pulls our :554, our RtspPuller pulls the caller’s :554. SipIntercomMedia feeds provider RTP into RtspServer.mic (what the caller hears) and forwards pulled PCMU as PT0 RTP to the provider peer. Audio-only by design. See protocol.md.

  • Outdoor/door calls via RTSP (caller class 1 / call to app / doorType>0, no m= lines): same RTSP pull model, plus an IntercomVideoLeg — the pulled door H264 stream is repacked as PT96 RTP and sent on a m=video provider leg, starting at the first SDP-bearing 18x (early media, video while the app rings).

  • Door calls (m=audio/m=video in the offer): classic RTP on the negotiated ports; RtpRelay bridges each direction to the provider leg.

  • Provider leg: PCMU/8000 PT0 only; RTP/SAVP + a=crypto when SRTP is on (default), RTP/AVP retry after a 488. No RTCP is sent.
