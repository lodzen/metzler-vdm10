2. Named config fields (V2 dump, shell_task_command_server @0x0008f56c)

The debug shell prints the SIP configuration as named fields — new-side vocabulary verified by literals:

  • SIP1.0 / SIP2.0 — protocol-generation status label

  • sipServerIpAddr / sipServerIpAddrV6

  • mainDoorIpAddr / mainDoorIpAddrV6

  • regToDoor / regToCenter / regToConfirm — per-target registration enable flags (roles 9/0xa in cli_send_regist)

  • sip server port: %d

  • plus IPv6 gateway fields (Gateway, IPV6 Gateway, set/del gateway, gatewayv6 DB column @0x00044e10).

mainDoorIpAddr:/devlongnum=%s, regToDoor=%d also appear in client code (@0x00147c9c, 0x00157b70, cli_get_subdoor_ip @0x00130038 region).

5. What a provisioning client must know

  1. regPassword (cfg+0x35a14) is a first-class field in V2 — it is the own-number HA1 input and part of the response-key derivation secret (%s_%s). Provisioning it wrong breaks both auth and the encrypted layer.

  2. Extension passwords are per-row in the device DB (sip_pwd column), not the station regPassword — see registration.md checklist item 4.

  3. The SIP1.0/2.0 byte changes which handler semantics run (compat vs auth, 410 gate) — a SIP-1.0 client needs “Compatible”/SIP1.0 mode or a provisioned password.

  4. IPv6 configuration exists end-to-end; on dual-NIC the secondary address is used for the same registration roles as V1.

  5. Don’t derive defaults from strings: SIP1.0/SIP2.0 labels and both code paths exist in the binary regardless of the configured value.
